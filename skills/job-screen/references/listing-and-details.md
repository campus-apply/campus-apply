# 清单与详情怎么读

## 节奏与并行

节奏分两档，整个 skill 通用：不登录就能看的页面，每次请求或翻页之间停 0.3–0.6 秒，最多 3 个标签页并行（`open` 各自认领、各跑各的进程，`read-urls` 用同一个 `--stop-file`，一处撞到验证码全部停）；登录后才能看的页面，单标签页，停 0.8–1.5 秒。表单页永远单标签页。

## 定读法（第 3 步）

到了列表页先看清单是怎么来的：`chrome_cdp.py --mark <ID> sniff <触发目标>` 让页面自己翻一页（触发目标是分页按钮的选择器，或 `js:` 调用页面自己的翻页函数），看它发出的请求里有没有返回 JSON 的。三种情况按顺序试：

① JSON 的字段里就有岗位正文（职责、要求）——走接口：在投递目录 `stages/` 写 stage 脚本，`--libs lib_net.js`，用 `__caNet.fetchJson` 复发同样的地址和请求体、只改页码，先读 2 条，把职责、要求、单位这几个字段和展开或点开后页面上的可见文本逐条比对，全部一致才读全量；每页之间 `__caNet.paced`。

② JSON 有但复发被拒（带签名、时间戳）——`__caNet.capture(() => 页面翻页函数(n))` 让页面自己发、截住它收到的 JSON，比对办法同上。

③ 没有 JSON、或 JSON 里没有正文——读 DOM，也就是下面"读详情"的三种形态。

走了哪条、请求样例、比对了几条，都记进站点笔记第一节。

## 读详情的三种形态（第 4 步）

第 3 步走了接口且正文随清单返回的，这一步已经完成，把正文写进 `jobs/<岗位>.md`、来源注明"接口（页面自己的请求）"；清单接口不含正文但点开详情另有请求的，对详情的触发动作再 sniff 一次，办法同第 3 步。其余情况详情有三种形态，先看清是哪种。

独立 URL：把要读的岗位写成 `id<TAB>url` 列表，`chrome_cdp.py --mark <ID> read-urls <列表> <输出目录> --pace 0.3-0.6` 逐个读（公开页；需要登录才能看的页面用 `--pace 0.8-1.5`），每 5 个自动 guard，验证码或跳登录自动停；公开页可以分成最多 3 段、3 个标签页各跑一个进程，带同一个 `--stop-file`。

弹窗或页内展开：在投递目录 `stages/` 现场写 stage 脚本，逐个点开、等正文出现、读完关掉，同样的间隔，每 5 个跑一次 guard。

三种形态下正文都存 `applications/<公司>/jobs/<岗位>.md` 并注明来源形态。读 DOM 时只记页面上看得见的文本，隐藏节点和模板占位里的值不算数；接口 JSON 里的字段按第 3 步抽样比对过才算数。分批跑，每批结束报进度。JD 是图片时截图存进 jobs/，看图读；看不清就请用户截图或口述。

## 预估要报两个数

**不要合成一个"大约几分钟"**：① 浏览器时间——正文随清单返回时就是 0（不用再开网页），要逐个打开详情才按每个约 4 秒估；② 模型读取量——要逐字读几份、合计多少字。prescreen 的 `estimate` 直接给这两个数，照着说。把它们混成一个区间是实测里踩过的坑：按 DOM 公式报了"39 份要 6～10 分钟"，而那个站正文早就随清单拿到了，浏览器时间是 0。

## 时间预算

从认领标签页到交出筛选表，**浏览器加模型合计不超过 5 分钟**。超了就是哪一步做多了——最常见的是抽样核对做太多份、或者现写脚本去排版。两样都有现成办法（抽样 2 份够了，出表用 `screen_render.py`）。
