# 筛岗的步骤

## 前提
- 当前目录有 `campus-apply.json`，其中 `preferences` 已填（没填先用 resume-facts 做偏好访谈）。
- 专用浏览器已启动并打开该公司的招聘页（`chrome_cdp.py launch <URL>`；没开就启动，并请用户在里面登录）。
- 浏览器操作用 `../../campus-apply/scripts/browser/chrome_cdp.py`（见总控 skill 的 `references/browser-tools.md`），配合同目录的 `guard.js`、`read_page.js`、`probe.js`、`lib_net.js`。
- 节奏分两档，见 `listing-and-details.md`。
- 开始时把 `checklist.md` 的执行清单复制成 `applications/<公司>/job-screen-执行清单_<日期>.md`，做到哪勾到哪。

## 开场先讲清这是两步走

筛岗分两步，**第一句话就要跟用户说明**，否则他会把第一步的等待当成白等：

> 我先用机器把全部 N 个岗位过一遍，按硬门槛分成三档（大概 X 分钟）；你从里面圈几个，我再逐字精读那几个、
> 给你适配性对照。

时间预算见 `listing-and-details.md`。

## 步骤
0. **偏好确认**：读 `campus-apply.json` 的 `preferences`，复述给用户（投什么、岗位类型要与不要、地点、海外、语言、提前入职），问这次投这家有没有变化，有就改写回去。用户看到清单（第 3 步）或摘要（第 5 步）后改主意很正常，那两处停顿里说的任何偏好变化当场写回，并据此重标状态。
1. **认领标签页**：`list <公司关键字>` 列给用户看，问用哪一个当工作标签页，`claim <序号>` 认领，之后所有命令带 `--mark <ID>`。专用浏览器没开（`list` 报 ERR_NO_CDP）或没有相关标签页时，`launch <URL>` 或 `open <URL>` 打开目标页（站点笔记里有就用具体地址），告诉用户"我开了一个专用的浏览器窗口，要登录请在这个窗口里登"，等用户说好；不碰用户日常的浏览器。然后明确说："接下来我只操作这个标签页，请不要碰它；其他窗口随便用。出现验证码我会停下来叫你。"站内导航如果开了新标签页或换了域名，立刻告诉用户并重新认领；绝不复用用户自己打开的其他页面。
2. **guard**：`chrome_cdp.py --mark <ID> exec guard.js`。`captcha` 为真就停下告诉用户；`loginRedirect` 为真或页面要求登录才能看岗位时，请用户在这个标签页登录，登录完再继续。
3. **列全量清单，定读法**：`read_page.js` 读当前页，判断这是门户页、类别页还是列表页（常见结构：门户 → 类别卡片 → 类别内岗位列表 → 岗位页）。到了列表页先按 `listing-and-details.md` 的"定读法"看清单是怎么来的（接口 / 页面函数 / DOM）。然后逐个类别、逐页读完，把全部岗位整理成 `applications/<公司>/岗位清单_<日期>.md`（格式见 `screen-output.md`）：名称、类别、性质、发布日期、链接（没有独立地址的站点写站内编号和定位方法，不写页码），列表页有的其他信息一并记，没有的留空；全量清单只落文件，终端和对话里只报数量、类别分布和前几行；站点规则按固定清单抽：可投几个岗、多个志愿之间的关系（同时推进还是有先后）、投后能否修改或撤回、内推码、届别或入职时间要求、截止日期、流程（笔试、测评、面试轮次）；去 FAQ / 常见问题 / 投递须知 / 招聘简章 / 岗位页提示这几处找，每条标出处（哪个页面、哪一段原话），两处说法不一致的两条都列出来让用户定，没找到的写"未见"而不是猜。摘进清单头部。这一步的产物只叫"岗位清单"，"岗位筛选"是第 5 步的名字。用户偏好里整体不投的类型（如实习、社招）不读，在清单里整段标明。然后**跑机器预筛**，不要自己肉眼过清单：`python3 <本skill>/scripts/prescreen.py <清单.json> --prefs campus-apply.json --facts <事实库…> --json 预筛_<日期>.json --md 预筛_<日期>.md`。它按偏好和能引用原文的硬门槛分三档——"读"（交给模型逐字读）、"待定"（要用户圈，如地点国内海外混排）、"排除"（每条带规则名和命中的原文片段），并算出两个代价。清单里字段名和站点不一致时用 `--map 目标键=来源键` 接。它只做能引用原文的判断：正文缺失、事实库没有学历口径、依据不足都进"读"或"待定"，绝不当成不符合；它也不给投递建议，选岗仍然是用户的事。
  预估要报两个数，见 `listing-and-details.md`。然后把三档的数量和"读"那一档的清单给用户，让他圈定或缩小；"待定"逐条问。告诉用户："如果你已经有心目中的岗位，直接告诉我，我只读那几个。"用量紧的先读一部分、看过摘要再补读。
4. **读详情**：三种形态与办法见 `listing-and-details.md` 的"读详情的三种形态"。
5. **摘要表给用户看**：每个读过的岗位一行——学历、专业要求、专业匹配、语言、地点、优先项、工作内容一句话、分档（建议投 / 可投但有缺口 / 不建议）、理由、缺口。地点、发布日期、性质这类结构化字段可以脚本抽；学历、专业、语言、优先项、工作内容必须逐份读 JD 由模型填，表头注明"模型读取"。JD 里出现的其他硬信息（届别或毕业时间要求、截止日期、招聘人数、薪资、工作时间等）读到什么记什么，作为额外列，没有的留空，整列空也保留，不猜。专业匹配以 JD 学历要求对应的那一层为准：要求硕士及以上看硕士专业，要求本科及以上则本科或硕士任一匹配即可；对应层不匹配、只有另一层匹配的记"专业缺口"，最高进"可投但有缺口"，理由写明哪一层不符；实习或工作经验不能抵专业硬要求，只在理由里作补充；"等相关专业"照抄原文，判为"相邻"而非"匹配"，按第 6 步问用户一句。分档同时看 JD 硬要求和用户偏好，偏好不符的进"不建议"并写明是偏好还是硬门槛。数据只落一份 `applications/<公司>/岗位筛选_<日期>.json`（字段见 `screen-output.md`），由它渲染其余三样：`python3 <本skill>/scripts/screen_render.py <json> --md <岗位筛选_<日期>.md> --xlsx <工作目录根/<公司>_岗位筛选_<日期>.xlsx>` 出 md 和带筛选箭头、按档着色、链接可点的 Excel，`--print 建议投,可投但有缺口` 打出对话里要贴的表（默认精简列，`--cols` 可换）。表格不手写，xlsx 也不用 harness 自带的表格或 artifact 工具再加工（筛选箭头、着色、链接都由脚本出，另做一份只会多出一份不同源的表）；对话里的表是 md、xlsx 的子集，三处同源。告诉用户完整表在哪个 xlsx；等用户说重点考虑哪几个、偏好有没有变。
6. **攒问题**：只对用户重点考虑的岗位，按 `screen-output.md` 的"提问三条件"攒问题，一轮最多 5 题，一次问完，每题带推荐答案；答案写回事实库（【用户口述 日期】）或 `preferences`。
7. **定稿**：按答案更新分档，问答记进筛选 md 末尾的"问答与定稿"。用户圈定投递岗位后建 `applications/<公司>-<岗位>/`，把对应 `jobs/<岗位>.md` 复制为 `jd.md`，站点规则（可投几个、第二志愿怎么填）抄进 `jd.md` 末尾。
8. **站点笔记**：写或更新 `site-notes/<域名>.md`（模板在 apply-fill 的 `templates/site-notes.template.md`）。只记**重新摸一遍要付代价**的那一类：清单和详情是怎么来的（接口 / 页面函数 / DOM，触发动作，请求方法与地址，只改页码的请求体样例，返回字段对应哪些信息，抽样比对了几条，用的间隔与并行数，最近核对日期）——重摸一次要向站点发几百个请求，值得记；以及投递规则（能投几个岗、投了还能不能改，标出处）。
   **URL 规律、翻页方式、侧栏混入的热招岗位、页面结构这些不要记**：现场读一眼就知道，而且站点一改版旧结论就会把人带偏。不写个人信息。
9. 把工作标签页导回列表页，在 `log.txt` 追加一行。
10. **交给 resume-tailor**：收尾时明确说下一步是针对这个岗位改一版简历，产出是一份这个岗位专用的 `resume.md` 和简历 PDF；填网申要等它跑完（apply-fill 的前提卡着这一条）。一岗一次，用户选了多个志愿就按第一志愿那个岗位改。不要直接跳到填表，也不要承诺"先把志愿页填上、简历一会儿补"。
