# 判断顺序与路由

## 做什么

只做一件事：看清现状，指到下一个 skill。四个功能 skill 都能单独用。
名词约定：岗位描述统一叫 JD；`launch` 起的那个浏览器叫专用浏览器。

## 判断顺序

0. 当前目录没有 `campus-apply.json`：先问一句"是第一次用，还是求职文件夹在别处？"
   在别处就切到那个目录再看；第一次用走 resume-facts 初始化（先看目录里有没有简历、事实类文件，列给用户）。
1. 有标记文件时，按下面的顺序判断这次要做什么。**不拿浏览器标签页猜**：专用浏览器是我们自己开的，
   里面的页面是上次留下的，不代表用户意向。
   - 这轮对话里给了公司招聘页链接 → job-screen
   - 给了 JD（文本或链接）→ resume-tailor
   - 说要填某个站点的在线简历 / 候选人档案页（没有具体岗位）→ 没有通用版 `resume.md` 就先走
     resume-tailor 的通用版，再 apply-fill
   - 说要填某个岗位的网申 → 该岗位有 `resume.md` 和简历 PDF 就 apply-fill，没有一律先 resume-tailor
     （apply-fill 的前提卡着这一条，不能先填志愿页再回头改简历）
   - 对话里没说清：列出 `applications/` 里还没有 `fill-report.md` 的投递目录（各有 jd / resume / form
     哪几样），问"继续哪一个，还是投新的"
   - 都没有：问"投哪家？给我招聘官网的链接，或者直接把 JD 贴给我"。只有公司名时可以提议由我去搜官网入口，
     但不主动找公司、不替用户挑公司

## 四步有先后

事实库 → 筛岗 → 改简历 → 填网申，**改简历没做完不开始填表**。

## 共用的执行约定

- 每个功能 skill 通过 skill 机制载入其 SKILL.md 再执行，不凭记忆跑。
- 状态更新、资料复用与交接按 `workflow-state.md`；执行清单的建法与勾法见 `checklists.md`。
- 只操作我们认领的浏览器标签页，不复用用户自己打开的页面；需要第二个页面时自己新开并认领。
- 页面没写的字段留空，不填 0、不猜；"若干"照抄"若干"。
- 填写素材优先取已确认且带来源的事实库；资料复用与冲突处理见 `workflow-state.md`。
- 反馈包（`../scripts/feedback_bundle.py`）只在用户明确说"打一个反馈包 / 导出反馈"时运行，
  不主动提议、流程结束不自动打包。交付前检查反馈摘要：无"agent 补"等占位，缺资料明确写无法确认；
  当前打包工具版本与历史会话实际载入的版本分开注明，不能相互代替。

## 浏览器接口的边界

不脱离浏览器调站点接口：不在浏览器外发请求，不伪造参数，不用页面自己没发过的地址。

可以做的：在认领的标签页里复发页面自己刚发过的请求（只改页码，job-screen 读清单和 JD 用，见其第 3 步）、
调用页面自带的、用户点按钮时同样会执行的前端函数（翻页、展开）——效果等于用户操作。

隐藏在 DOM 里已经下发但用户看不见的内容，仍只在展开可见后读。
页面自己请求返回的 JSON 只在 job-screen 读岗位清单和 JD 时用，且先抽几条与页面可见文本比对一致。
