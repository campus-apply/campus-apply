# 现场处理原则

每个站点的板块划分、控件、弹窗、分步流程都不一样。本 skill 只给办法，不给死代码：填写脚本每站现写，`lib_antd3.js` 只是一套参考实现。具体选择器以探测结果和现场 DOM 为准。

## 先等页面稳定
- 刷新或导航后表单是分批渲染的，头几秒只有少数控件；探测至少做两次、间隔两秒，控件数不再变化才算稳定，否则会把没加载完的页面当成空表。

## 控件类型先探清楚
- 静态分类：看标签、placeholder、class、有没有下拉箭头或日历图标，把每个控件归为文本、纯下拉、可搜索下拉、日期面板、级联、复选、文件之一。`probe.js` 标成 `dropdown?` 的只是"像下拉"（旁边有显示值元素、箭头图标或弹出属性），是纯下拉、可搜索还是级联要靠行为探测定；`disabled` 的字段写不进，`readonly` 的多半是面板类。
- 分不出来的做一次无害的行为探测：点一下看有没有面板或菜单出现，输一个字符看有没有建议项，然后恢复原值并关掉。只在表单还是空的时候做。
- 结论写进填写计划，**不写进站点笔记**——控件类型、选项列表、选择器这些探起来只要几秒，而且同一个域名下换一页就可能不一样，记下来反而会把下次带偏。可搜索下拉（年、月、学校名称这类）最容易被当成文本框：值要靠点菜单项才算选中，选中后显示在另一个元素里，输入框本身可能是空的。

## 明示的字段范围
- 只对页面明确限定的字段，在 `fill-log.md` 记字段名、要求原文及来源位置、可用素材范围。例如“国家级荣誉”只取国家级荣誉，实习经历不混入校园经历；没有明示限制的普通字段不额外建规则。
- 初填、追加、导入旧申请和事故恢复都复核当前范围。旧记录确认过只能证明素材有来源，不能证明适合本站这个字段；没有硬校验、能保存也不代表符合页面要求。
- 用户说“全部补齐”时，按当前字段范围补齐；范围外素材有合适位置就说明替代位置，没有就暂留资料中，不先写进去再解释。
- 用户要求范围外内容时，在工具结束后的交接中说明限制、哪些内容不符合及可用替代位置，等明确答复再做依赖写入。如果用户已明确理解限制、仍明确坚持，记录其答复与时间后照其决定执行，报告注明“用户知情选择范围外内容”，不称为符合要求。

## 长文本的字数限制有三层
- `maxlength` 属性只拦键盘输入，脚本写入拦不住；页面明文（"200-1000 字""不超过 500 字"，probe 报为 `hintLimit`）是招聘方的要求；真正生效的是保存或失焦时的校验，可能按字符也可能按字节。
- 探测阶段对空着的长文本字段做一次无害的长度试探：按页面明文上限多写一点 → 触发失焦 → 读新出现的错误提示 → 恢复为空。把校验得出的真实上限（和单位）记进 `limits.json`（`{"min": 200, "max": 1000, "unit": "字"}`）。
- 属性、明文、校验三个值不一致时，全部列给用户并注明来源和试探结果，由用户定按哪个写。
- 写入脚本自己遵守 `limits.json`，写完回读时扫一遍新出现的错误提示，有就按写入失败处理。

## 面板必须收起
- 每打开一个下拉、日历、级联面板，同一步骤内必须关掉并验证已关。
- **面板按点击前后的变化找，不按 class 猜。** 点之前先盯住页面，点之后新出现的那个就是面板——面板是点出来的，这是它和页面上那些长得像面板的常驻容器唯一可靠的区别。几何位置（横向重叠、纵向远近）只用来在多个候选里排序，**不拿来淘汰**：有的站点面板不在输入框上下方，而是盖在它身上。按 class 全局列举会两头落空：真面板可能被同样命中选择器的祖先容器吞掉，而行内常驻容器会被当成"开着的面板"，让整页填完也报不干净。
- **收面板不写死顺序，现场试。** 几种办法依次试：再点一次输入框 → 点该字段的标签 → 让输入框失焦 → 点所在板块的标题 → 对同一目标派发合成的 `mousedown` + `mouseup` + `click` 序列（有的组件只认 `mousedown`）→ 用 `chrome_cdp.py click` 发真实鼠标事件。哪一招奏效就记下来，本页后续字段先试它。**不要把顺序当成偏好定死**：实测过两个站点，一个站"再点一次输入框"十次全中、"点字段标题"十次全不中，另一个站正好反过来。`fill` 自己会试、会记，并在报告的 `close_trick` 里告诉你本页用的是哪一招。
- 行为探测也一样：开一个、关一个、验证已关，再探下一个；连续开着探会叠出十几层面板。
- 禁止 `document.body.click()`，禁止键盘事件。
- 整页填完再检查一次"我们自己开的面板为零"，不为零不算完成。注意这个数只算**自己点开过、现在还可见**的面板，不是"页面上有多少节点长得像面板"——后者在某些站点恒为几十个，拿它当判据会让整页永远填不完。

## 别让浏览器干等着

- 页面加载好、登录着、什么命令也没在跑的那段时间是纯损耗。实测里它比命令本身长一倍以上，而大头不是工具慢，是**模型在手工维护坐标表**：先把控件下标抄一遍，写计划时再按新下标算一遍。所以字段表交给 `plan-skeleton` 出，探测交给 `survey` 一次读完，自己只填值。
- **记录类的工作放在 `fill` 跑着的时候写。** `fill` 一跑就是几十秒到几分钟，这期间浏览器在忙、模型闲着，正好写 `fill-log.md`、准备下一页的骨架、整理待办。反过来，`fill` 跑完了才开始写日志，那几分钟浏览器就白等了。
- 但**不要在 `fill` 跑着的时候碰浏览器**：页面正在变，`probe` 或 `exec` 读到的是中间态，两条命令还会抢同一个标签页。只做不碰浏览器的事。
- 想知道这一轮空置了多久：开 `CA_TIMING_FILE`，结束后跑 `scripts/idle_report.py`，把"命令占用 / 浏览器空置"写进 `fill-report.md`。不量就只能凭感觉，而感觉一直是错的——总耗时里最大的一块恰恰最不显眼。

## 写入走 fill，探测才现写脚本
- 写字段的默认办法是 `chrome_cdp.py --mark <ID> fill <计划.json>`：每页产出一份计划 JSON（字段名、选择器、控件类型、目标值），一条命令在页内连续填完整页并返回逐字段报告。用法见总控的 `references/browser-tools.md`。
- 不要为每个字段现写 stage 脚本。2026-10-04 的实测：同一页十个字段，`fill` 是 1 次命令、中位 3.1 秒；每字段一个 stage 脚本是 16 次命令、中位 6.5 秒，两者终态一致（`evals/fill_benchmark.py`）。真正的代价不在这几秒，而在每写一个字段就要模型现写一个文件、再往返一次。
- 现场写脚本仍然用于**探测**：探控件类型、试长度上限、读页面结构。探明白了就把结论落进计划，别用脚本去写值。
- 计划自己守 `limits.json`（字段给 `max`），不指望 `maxlength` 拦。
- `fill` 不碰提交，也不翻页：进入表单的入口按钮、**下一步 / 上一步**、保存、暂存、投递都不在它的动作里。
- 整页重跑的要求不变：计划是幂等的（同一份计划重跑一次，结果一样），填写日志里留全量目标值，出事故能整页重填。分步表单是"一步一份计划"，不是"整个流程一份计划"。

## 回读分三层
- 显示值、DOM `value`、框架模型值三层都读（写法见 `controls.md`）。**显示值和 DOM 一致就算写进去；框架模型值只作参考，读不出或不一致只记一条警告，不单独否决。** 因为模型层靠猜框架内部结构，本身不可靠：React 的 fiber 在奇数次提交后，挂在元素上的那个会指向旧分支，直接读它会把写对的值判成没写进去（2026-10-04 为这个假阳性返工了 1 分 53 秒）。真正能证明存上了的是下面"保存后刷新逐字段比对"，举证责任放在那里。
- 下拉读显示值元素，文本读 `value`，日期读显示值；输入框 `value` 为空不等于没填。
- **探测报空也不等于没填。** 容器型控件（日期选择器、下拉的外层是 span 或 div）的值在内层 `input` 上或显示元素的文本里，按容器读只会读到空。`probe.js` 现在分三层取值并用 `valueFrom` 说明读自哪一层（`self` / `inner-input` / `display`）；三层都拿不到时报 `valueUnknown: true`、`valueLen: null`，这是"读不出"，不是"是空的"。
- **`valueUnknown` 的字段一律不许触发补填、清空或覆盖**，先只读确认那个字段现在到底有没有值，确认不了就列给用户。把"我判断不出 X"当成"X 不成立"，是这个工具唯一能弄坏用户真实数据的方式。
- 证件号、密码、验证码、银行卡号这类字段回读只记"有值 / 长度"，不把内容写进回读文件或日志，用户自己填的也一样。
- `disabled` 的字段（常见于账号级的姓名、手机、邮箱）写不进去，探测时先标出来，告诉用户去账号设置页改。
- 校验提示（"必填项未填写"）可能滞后于实际值，不能拿它当填没填的判据。
- 条件字段（选了某项才出现的字段）探测不到，填完一轮回读才会看到，要再填一轮。

## 分步、暂存、弹窗
- 分步表单（"下一步""上一步"）：**一步一份计划**，只写当前激活那一步里的字段，写完回读通过才进下一步；点前跑 guard，点后等页面稳定再探测。"下一步"由用户点还是我点，第一次遇到时问用户定一个规矩——`fill` 自己不会点它，也不点保存、暂存、提交。
- 下一步的字段**即使已经在 DOM 里也不要放进计划**。隐藏控件能被脚本写进去，三层回读还会通过（读到的就是刚写的值），报告会显示 `OK`，可用户什么都看不见、站点换步时还可能丢。`fill` 现在会拦住这种字段并报"控件在 DOM 里但不可见"；看到这条不要按控件失败的规矩整页重跑两遍，先判断它是不是在下一步。
- 同理，`fill` 报"找不到控件"时也先想一步：条件渲染的站点，下一步的字段压根不在 DOM 里，这是正常的，翻页之后再出一份新计划。
- 填写期间页面导航了（站点的失焦自动保存、用户手点了下一步），`fill` 会打印 `ERR_CONTEXT` 并退出非零；逐字段报告仍然会打出来，但那是页面变化之前的状态，要只读核对当前页面再决定补填哪些。
- "暂存""临时保存""保存草稿"默认不点，用户明确说要点才点；真正的"提交""投递"永远不点。
- 弹窗：先分清是我们触发的（删除确认、日期面板）还是站点弹的（引导、公告、验证）。前者一次触发一次处理；后者只读内容告诉用户，让用户决定关不关。
- 自动识别简历附件带出的占位内容只当占位，逐字段重写。
- class 带发版哈希后缀时用前缀匹配 `[class^="xxx-"]`。
